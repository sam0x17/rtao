## 0. TL;DR

1. `bittensor-core` is a ~400 KB-of-source (29 `.rs`/`.cl` files incl. in-file tests), `publish = false`, version-`0.1.0` rlib (`$CORE/Cargo.toml:3-5`) inside the subtensor cargo workspace (`$SUB/Cargo.toml:27-39`). It is the native module behind the PyPI package `bittensor-core` (0.1.5 stable on 2026-10-07, 0.1.6rc68 on 2026-10-08 **(web)**) and is consumed by the Python SDK only through the `bittensor_core` extension (`$SUB/sdk/python/pyproject.toml:21,59-60`).
2. It has grown past its own spec: the spec declares "No Rust websocket/RPC transport", "No Rust codegen or intent layer" as non-goals (`$SUB/sdk/bittensor-core-spec.md` §3), yet the crate now ships a blocking HTTP JSON-RPC `Client` (`$CORE/src/client.rs`) and an `IntentCall/Policy/Plan/Executor` layer (`$CORE/src/transaction.rs`), and `lib.rs:1-6` calls itself "the chain-defined compute core **and native Rust SDK**". That "SDK" is used as the e2e harness for the chain (112 tests, `$CORE/tests/e2e.rs`) and is not documented or published as a product.
3. The chain-defined pieces are small, self-contained modules with concrete byte formats: ss58/sr25519/ed25519 (`keys/`), four keyfile envelopes (`keyfiles/`), drand tlock ciphertext + reveal-round math + commit-v2 payload (`timelock/`), ML-KEM-768 shield blob (`mlkem/`), RFC-0078 digest + Ledger proof (`digest/`), v4 signed-extrinsic assembly driven by the metadata extension table (`codec/extrinsic.rs`), multisig id, PoW v1 challenge (`pow/`), Ledger HID/APDU (`signers/`).
4. The codec is a metadata-driven dynamic-`Value` engine whose output shapes are *cyscale's Python shapes* (ss58 strings for AccountId32, `{"Variant": payload}` dicts, utf8-else-hex for `Vec<u8>`) pinned by a 2,899-sample shape corpus (`$CORE/src/codec/decode.rs:1-8`, `$SUB/sdk/python/tests/fixtures/shape_corpus/corpus.json`). This is a Python-compatibility contract, not a Rust-idiomatic type system.
5. Dependency reality: `sp-core` is a **git dependency on the RaoFoundation/polkadot-sdk fork** (`$SUB/Cargo.toml:227`, lock resolves sp-core 37.0.0), `tle` is a **git dependency** (`$SUB/Cargo.toml:310`), `w3f-bls` is a **vendored path crate applied through `[patch.crates-io]`** (`$SUB/Cargo.toml:299,334-335`), and `subtensor-macros` is a path proc-macro crate (`$SUB/Cargo.toml:74`). Three of these make a crates.io publish impossible as-is; the `[patch]` does not propagate to anyone consuming the crate as a git dependency.
6. C/system deps on the default `host` feature: libsodium (sodiumoxide), vendored OpenSSL (fernet), ring (reqwest/rustls), secp256k1-sys (sp-core/std), hidapi C backend on macOS/Windows (`$CORE/Cargo.toml:24-62,86-94,105-126`; `$SUB/Cargo.lock` has libsodium-sys, openssl-src, ring, secp256k1-sys). Without `host`, the crate compiles for `wasm32-unknown-unknown` and CI enforces it (`$SUB/.github/workflows/check-rust.yml:274-302`).
7. The transport is `reqwest::blocking` HTTP POST JSON-RPC; `ws://` URLs are rewritten to `http://` (`client.rs:1300-1308`); there are no subscriptions, block "streams" are polling iterators (`client.rs:338-355,1115-1158`), receipts are found by polling `chain_getBlock` per block (`client.rs:897-962`). It is structurally incompatible with a tokio-first design.
8. Versioning: the Cargo version is never stamped (static `0.1.0`); only `$PY/pyproject.toml:9` (`0.1.6`) is stamped by CI (`$SUB/.github/workflows/build-core-wheels.yml:46-63`), rc suffixes come from `GITHUB_RUN_NUMBER` (`release-train.yml:307-350`), stable wheels publish from `watch-mainnet-release.yml` after the mainnet upgrade executes (`$SUB/docs/internals/release-process.mdx:98-122`). The crates.io name `bittensor-core` is unclaimed (HTTP 404 from the crates.io API **(web)**).
9. Reusable fixtures: `golden.json` (1.5 MB, spec 461, 10 storage keys, 10 calls, 2 payloads, 2 extrinsics, 3 multisigs, 4 ss58, raw V14+V15 metadata), `shape_corpus/corpus.json` (1.08 MB, 797/802 types, 2,899 samples), `ledger_proof_vector.json`, epoch-schedule vectors, in-code PoW/twox/digest vectors. There are **no** byte-exact keyfile encryption vectors anywhere (keyfile "golden" tests are round-trips only: `$SUB/sdk/python/tests/unit/test_keyfiles_golden.py:45-85`).
10. Recommendation (details in §9): do **not** depend on or fork the crate wholesale. Reimplement in rtao against the same fixtures (option d), vendoring with attribution only the handful of self-contained format modules (keyfiles, timelock epoch-schedule/commit-v2, mlkem, pow, Ledger HID framing) and keeping an upstream-diff script for exactly those files. Treat (a) git-dependency as a non-starter for a crates.io-published rtao and (b) upstreaming as a parallel, non-blocking ask.

## 1. Provenance, status and intent

- Design document: `$SUB/sdk/bittensor-core-spec.md`. Status line: "implemented through phase 4 (branch `bittensor-core-exploration`, 2026-07-10)"; phases 0-4 = corpus + scaffold, consolidation of `py-sp-core` + `bittensor-drand`, RFC-0078 digest + `LedgerSigner`, Rust runtime/codec replacing cyscale/xxhash/`TYPE_REGISTRY`, payload/assembly/multisig with byte-equal goldens. Phase 5 ("uniffi/napi bindings, id-based descriptor fast path") is "unscheduled by design".
- Spec §1: "one pure-Rust library crate in the monorepo workspace, pinned to the same `sp-core` / `frame-metadata` revisions as the runtime. No binding code inside"; "Python keeps everything whose right answer is a product decision; Rust keeps everything whose right answer is defined by the chain."
- Spec §3 non-goals: no Rust websocket/RPC transport (benefit measured ≤7%), no Rust codegen or intent layer, no behavior changes, no Rust `btcli`.
- Reality drifted from §3: `client.rs:1-8` ("`Client` is the small blocking JSON-RPC layer... works in ordinary Rust tests, command-line programs, and foreign-language bindings alike") and `transaction.rs:1-5` ("Semantic transaction planning and policy for the native Rust SDK"). The wasm binding crate (`$WASM`) also exists although the spec only mentions it as a future sibling.
- What the monorepo calls it: root README line 51 "Client core... The Rust core for Bittensor clients ... Python bindings in `sdk/bittensor-core-py/`"; `$SUB/docs/internals/repo-layout.mdx:40-41`; `$SUB/docs/internals/testing.mdx:16` lists "Rust SDK e2e | Chain-facing SDK behavior against localnet | `cargo test -p bittensor-core --test e2e`". No page under `docs/` (sdk.mdx, agents.mdx, guides/) mentions a Rust SDK as a product (grep over `docs/*.mdx` and `docs/guides/*.mdx` finds nothing; only `internals/repo-layout.mdx` and `internals/testing.mdx` mention the crate).
- Spec §10 performance claims (self-reported acceptance run 2026-07-10, not verified here): `Runtime::parse` 4 ms; decode 60-77 MB/s; `compose_call` <50 µs; sign+assemble 0.03 ms; `query_map` decode 599k entries/s.
- PyPI timeline **(web, pypi.org JSON)**: first upload `0.1.0rc6` on 2026-07-13; stable `0.1.0`...`0.1.5`; `0.1.5` on 2026-10-07; `0.1.6rc68` on 2026-10-08; wheels are `cp310-abi3` for `manylinux_2_17_x86_64`, `manylinux_2_28_aarch64`, `macosx_10_12_x86_64`, `macosx_11_0_arm64`, plus sdist. The spec's packaging note matches: "`py-sp-core` and `bittensor-drand` are frozen, not shimmed" (§9).

## 3. Module-by-module public API inventory

Legend: **CHAIN** = chain-defined (must never drift; a wrong byte is rejected on-chain or produces an unreadable artifact); **COMPAT** = defined by an external ecosystem format (btwallet/polkadot-js/Ledger) rather than the chain; **PRODUCT** = convenience/policy that rtao is free to redesign.

### 3.1 `error.rs` (PRODUCT)

`CoreError { Keyfile, WrongPassword, NotInRuntime, Codec, Crypto, Device, Rpc, Policy }`, each carrying a `String` (`$CORE/src/error.rs:10-30`); `Display` + `std::error::Error`. Mapped once per binding: Python `KeyfileError`/`WrongPasswordError`/`KeyError`/`ValueError`/`LedgerError`/`ConnectionError`/`PermissionError` (`$PY/src/errors.rs:29-39`); JS `Error.name` strings (`$WASM/src/errors.rs:8-25`).

### 3.2 `keys/` — ss58, sr25519/ed25519, sealed box, encrypted-JSON import

`$CORE/src/keys/mod.rs`:

- Constants: `CRYPTO_ED25519 = 0`, `CRYPTO_SR25519 = 1` ("matching the py-substrate-interface / btwallet convention"), `DEFAULT_SS58_FORMAT = 42` (27-31). **COMPAT** (the numeric code is a btwallet keyfile convention, see `cryptoType` below).
- `public_key_from_ss58(&str) -> [u8;32]` via `sp_core::crypto::AccountId32::from_ss58check` (48-52). **CHAIN** (ss58 checksum rules).
- `ss58_from_public([u8;32], u16) -> String` (57-77): hand-rolled `"SS58PRE" ++ prefix(1-2 bytes) ++ key ++ blake2b-512[..2]` and a limb-based base58 (`keys/base58.rs:1-80`, 58^5 per division) claimed ~6x faster than bs58; equivalence with `sp-core` pinned by a 400-case test (480-498) and base58 vs `bs58` (base58.rs:88-120). **CHAIN**.
- `Keypair` (151-162): `KeypairInner::{Ed25519(sp_core::ed25519::Pair), Sr25519(sp_core::sr25519::Pair), PublicOnly{public_key, crypto_type}}` plus retained `mnemonic: Option<Zeroizing<String>>` and `seed: Option<Zeroizing<Vec<u8>>>` "for parity with the legacy btwallet format that third-party tools parse" (154-161).
- Constructors: `new(ss58, public_key, crypto_type, ss58_format)` public-only (166-208); `from_mnemonic(mnemonic, crypto_type, password)` via `Pair::from_phrase` (211-240; phrase retained only when no derivation password); `from_seed` (243-261); `from_uri` (sp-core SURI with junctions, 264-284); `from_private_key(hex)` (sr25519 64-byte secret or ed25519 ≥32-byte seed, 287-319); `generate_mnemonic(12|15|18|21|24)` via `bip39` crate (322-334); `from_encrypted_json(json, passphrase)` **host only** (338-340).
- Accessors: `crypto_type`, `public_key_bytes`, `ss58_address`, `ss58_format`, `private_key_bytes` (sr25519 → 64-byte schnorrkel secret; ed25519 → 32-byte seed via `to_raw_vec`), `mnemonic()`, `seed_bytes()` (342-378).
- `sign(&[u8]) -> Vec<u8>` raw 64-byte signature (391-399). `verify(message, signature)` tries raw then **`<Bytes>...</Bytes>`-wrapped** message ("Matches btwallet's `<Bytes>` wrapping fallback", 402-410); free `verify(message, sig, ss58, crypto_type)` (457-469). **CHAIN** for signing; the `<Bytes>` wrap is a wallet-ecosystem convention inherited from btwallet (**COMPAT**).
- Sealed box (host only): `encrypt`, `decrypt`, `encrypt_for` — libsodium `sealedbox` over ed25519→x25519 converted keys (102-126, 414-453). **COMPAT** (btwallet feature).
- `keys/encrypted_json.rs` (host only): polkadot-js keystore v3 import: `PKCS8_HEADER` / `PKCS8_DIVIDER` byte constants (18-19), scrypt header `salt[32] ++ N(u32 LE) ++ p(u32 LE) ++ r(u32 LE)` with caps `log_n ≤ 18, r ≤ 8, p ≤ 1` to stop CPU-DoS (83-98, 114-144), `secretbox` nonce 24 + ciphertext (149-159), sr25519 secret from `schnorrkel::SecretKey::from_ed25519_bytes` (48-53, 162-168), ed25519 from the first 32 bytes (169-180). Only `version == "3"` accepted (106-108). **COMPAT**.

### 3.3 `keyfiles/` (host only) — btwallet on-disk formats (COMPAT, must not drift)

`$CORE/src/keyfiles/mod.rs`:

- Detectors by prefix: `$NACL` → "NaCl", `$ANSIBLE_VAULT` → "Ansible Vault", `gAAAAA` → "legacy" (Fernet) (29-57).
- NaCl: key = `argon2i13::derive_key(password, NACL_SALT, OPSLIMIT_SENSITIVE, MEMLIMIT_SENSITIVE)` with the fixed 16-byte salt `\x13q\x83\xdf\xf1Z\t\xbc\x9c\x90\xb5Q\x879\xe9\xb1` (22, 59-72); layout `b"$NACL" ++ nonce[24] ++ secretbox(ciphertext)` (74-95). Encryption writes this format; decryption also accepts the other two.
- Ansible Vault: `ansible_vault::decrypt_vault` (165-170) — decrypt-only in the core (tests encrypt with the crate for round-trips, 407-415).
- Legacy Fernet: key = `pbkdf2_hmac::<Sha256>(password, LEGACY_SALT = b"Iguesscyborgslikemyselfhaveatendencytobeparanoidaboutourorigins", 10_000_000 iterations)` → urlsafe-base64 Fernet key (23, 140-151) — this is why `openssl` (vendored) is in the tree (`$CORE/Cargo.toml:27-32`).
- Env-var password helpers: `get_password_from_environment` / `save_password_to_environment` XOR the password with the env-var name and base64 it; uses `std::env::set_var` with an explicit "not thread-safe" comment (111-138).
- Keyfile JSON: `serialized_keypair_to_keyfile_data` writes `accountId`, `publicKey`, `secretPhrase` (when retained), `secretSeed`, `privateKey`, `ss58Address`, `cryptoType` (179-209). `deserialize_keypair_from_keyfile_data` accepts: the legacy `" ss58Address"` key with a leading space (213-218); `cryptoType` as number **or numeric string** (318-327); derivation order `secretPhrase` → `secretSeed` → `privateKey` → `ss58Address` (329-364); cross-checks the derived address against the stored `ss58Address` and **retries with the other crypto type** on mismatch (224-254); raw non-JSON fallbacks for a bare hex seed (64 hex), bare 128-hex private key, or a bare mnemonic (258-285); polkadot-js exports get an actionable error pointing at `btcli wallet regen-coldkey --json-path` (311-316).

No encrypted-blob golden vectors exist; the tests are round-trips (`keyfiles/mod.rs:388-428`; Python `test_keyfiles_golden.py:45-85` is also round-trip only).

### 3.4 `timelock/` — drand quicknet tlock + commit-reveal v2 (CHAIN + PRODUCT mix)

`$CORE/src/timelock/constants.rs`: `MAX_TEMPO = 50_400` (6); `DRAND_PUBLIC_KEY` (14, quicknet BLS pk); `GENESIS_TIME = 1_692_803_367` (17); `DRAND_PERIOD = 3` (20); `QUICKNET_CHAIN_HASH = 52db9ba7...e971` (23-24); five public HTTP endpoints (27-33); `SECURITY_BLOCK_OFFSET = 3` (39); `COMMIT_INCLUSION_BLOCK_OFFSET = 1` (44); `max_simulation_blocks(reveal_period) = reveal_period*MAX_TEMPO + MAX_TEMPO` (47-51).

`$CORE/src/timelock/mod.rs`:

- `WeightsTlockPayload { hotkey: Vec<u8>, uids: Vec<u16>, values: Vec<u16>, version_key: u64 }` SCALE struct with `#[freeze_struct("705b0f6dde3ed6e")]` (51-58). The chain's copy is field-identical: `$SUB/pallets/subtensor/src/coinbase/reveal_commits.rs:19-26` (`freeze_struct("b6833b5029be4127")`; the hash differs only because `freeze_struct` hashes the whole item including the attribute text that follows it, and the SDK puts `#[derive(...)]` after the attribute — `$SUB/support/macros/src/lib.rs:43-56` **(inferred from the macro impl)**). The chain also decodes a `LegacyWeightsTlockPayload` without hotkey (`reveal_commits.rs:29-35, 155-166`). **CHAIN**.
- `UserData { encrypted_data: Vec<u8>, reveal_round: u64 }` (60-65) is the SDK's portable envelope; it does **not** exist in the pallets (grep for `struct UserData` finds nothing) — the chain calls take the inner ciphertext and the round separately (`commit_timelocked_mechanism_weights { netuid, mecid, commit: BoundedVec<u8>, reveal_round: u64, commit_reveal_version: u16 }` and `Commitments.set_commitment` `Data::TimelockEncrypted { encrypted, reveal_round }`, via `subxt explore` on `$META/finney.scale`). `reveal_round()` / `inner_ciphertext()` unwrap it (87-100). **PRODUCT** (SDK/btcli convention; also baked into the Python `Timelocked` object).
- `encrypt_and_compress(data, round)` (104-140): identity = `Identity::new(b"", vec![sha256(round.to_be_bytes())])`, `tle::<TinyBLS381, AESGCMStreamCipherProvider, OsRng>(pk, esk[32], data, identity, OsRng)`, output `serialize_compressed`. The chain decrypts with exactly `TLECiphertext::<TinyBLS381>::deserialize_compressed` + `tld::<TinyBLS381, AESGCMStreamCipherProvider>` and requires 32-byte `header.v`/`header.w` (`reveal_commits.rs:91-129`). **CHAIN** — and the ciphertext bytes depend on the exact `tle` rev + `w3f-bls` copy; this is the coupling the vendoring exists for.
- `decrypt_and_decompress(ct, sig)` (143-155). `decrypt_with_signature(envelope, sig_hex)` (319-325) portable; `decrypt(envelope, no_errors)` and `get_round_info`/`get_reveal_round_signature` fetch from drand over **blocking reqwest** (host only, 242-315).
- `generate_commit_v2(uids, values, version_key, state: EpochScheduleState, reveal_period_epochs, block_time: f64, hotkey) -> (ct, round)` (160-195): predicts the first reveal block, adds `SECURITY_BLOCK_OFFSET`, converts to seconds with wall-clock `SystemTime::now()` and `block_time`, `round = floor((target_secs - GENESIS_TIME)/3)`, min 1. **PRODUCT** (a client-side heuristic; the chain only checks the round when revealing).
- `encrypt_commitment(str, blocks_until_reveal, block_time)` (199-213), `encrypt_n_blocks` (217-226), `encrypt_at_round` (230-238, UserData envelope). **PRODUCT** wrappers over the CHAIN primitive.
- `epoch_schedule.rs`: `EpochScheduleState { last_epoch_block, pending_epoch_at, subnet_epoch_index, tempo, blocks_since_last_step, current_block }` (17-24); `should_run_epoch` ("Port of `run_coinbase.rs:1043-1057`", 45-59); `current_epoch_pre_run_coinbase` ("Port of `weights.rs:1275-1282`", 63-70); `simulate_run_coinbase` ("Port of `run_coinbase.rs:337-403`... ### 4.4 Is it intended as a public Rust SDK?

Evidence for "internal harness + binding core", not product: `publish = false` and never-bumped `0.1.0` (`$CORE/Cargo.toml:3-5`); the only consumers in-tree are the two binding crates (neither exposes `Client`) and `tests/e2e.rs`; the docs describe it as "the chain-defined compute core for clients" with "Python bindings" (`repo-layout.mdx:40-41`) and the e2e harness (`sdk-tests.mdx:73-83`, `testing.mdx:16`); the e2e PR classifier calls it "the native bittensor-core Rust harness" (`$SUB/.github/scripts/classify-bittensor-e2e-changes.sh:55-58`); no docs page or changelog mentions a Rust SDK. Evidence for ambition: `lib.rs:1-6` ("native Rust SDK"), `client.rs:7-8` ("works in ordinary Rust tests, command-line programs, and foreign-language bindings alike"), the wasm sibling crate. Net: a working but unpublished, unversioned, blocking "native SDK" whose primary job is to be the chain's e2e test harness.

## 9. Frank assessment and options for rtao

### 9.1 What is genuinely valuable in this crate for rtao

- The exact byte formats and the places they are pinned (§3.14 table), especially: keyfile envelopes and the quirky keyfile JSON reader (`keyfiles/mod.rs:213-364`), the fixed NaCl salt and 10M-iteration Fernet KDF, the tlock identity/round math and `WeightsTlockPayload`, the shield envelope, the PoW v1 prefix, the Ledger APDU/HID details, the extension-table-driven payload assembly and the `modlpy/utilisuba` derivation, and the RFC-0078 `ChainInfo` constants.
- The fixtures (§8) — rtao can run the same `golden.json` call/storage-key/payload/extrinsic/multisig cases and the ledger proof vector as cross-implementation tests with zero porting of the Rust engine.
- The e2e harness design (per-test disposable localnet, manifest-pinned test list, `E2E_ENDPOINT` override, PR image with `SUBTENSOR_LOCALNET_RUNTIME_WASM`) is a good template for rtao's own integration tests, and the published localnet images (`ghcr.io/raofoundation/subtensor-localnet:{devnet,testnet,mainnet,main,latest}`, `release-process.mdx:127-138`; `docs/guides/local-development.mdx:13-15`) are directly reusable.

### 9.2 What is a poor fit for rtao's goals

- Sync/blocking everywhere (`reqwest::blocking`, `thread::sleep` polling, `Mutex<HidDevice>` blocking reads, drand fetch) versus "tokio ecosystem / async".
- Dynamic `Value` codec shaped like Python dicts versus a typed Rust SDK (subxt-style codegen is what makes `set_weights(netuid, dests, weights, version_key)` a compile-time-checked call).
- Heavy, git-pinned, fork-only dependency graph; C toolchain requirements; two `w3f-bls` copies.
- No semver, no changelog, no crates.io presence, `publish = false`; API evolves with the monorepo's internal needs (the spec itself was overtaken by `client.rs`).
- v4-only signed extrinsics while the chain already declares `[4, 5]`; V15-only metadata parsing.

### 9.3 Options

**(a) Git-dependency on the monorepo crate pinned to a runtime tag (e.g. `tag = "v477"`).**
- Pros: zero reimplementation of chain-defined formats; stays byte-identical with what the Python SDK ships; upstream's unit tests/goldens/e2e cover it.
- Cons: rtao could then never be published to crates.io (git deps are rejected); every `cargo update`/fresh CI clones the subtensor monorepo and the polkadot-sdk fork; Cargo honours workspace inheritance for git deps but **not** the root `[patch]` table, so `tle` would resolve crates.io `w3f-bls` (risk of picking 0.1.9 and failing to compile, or silently differing from the vendored copy — unverified either way) and `sc-informant`/zstd patches are irrelevant but the fork-vs-opentensor duplicate-source patch is also gone; default `host` feature drags libsodium/OpenSSL/ring/secp256k1 C builds into rtao; blocking API must be wrapped in `spawn_blocking`; no API stability promise; one unpublished proc-macro crate (`subtensor-macros`) comes along. Verdict: only viable as a temporary, non-published spike.

**(b) Upstream a crates.io release.**
- Required upstream changes: swap git `sp-core` for crates.io `sp-core` (or drop it for `schnorrkel`+`ed25519-zebra`+`bs58`+`blake2`, since only sr25519/ed25519/ss58/blake2/twox/keccak are used), replace git `tle` with crates.io `timelock` (and prove ciphertext equality against `pallets/subtensor/src/coinbase/reveal_commits.rs:91-129`), publish or remove `subtensor-macros` (`freeze_struct` is a compile-time guard only), drop the vendored `w3f-bls` `[patch]` dependency, set `publish = true`, stamp Cargo versions in the release train, add a publish job, and decide what `Client`/`transaction` mean publicly (or feature-gate them off).
- Pros: one maintained implementation for everyone; rtao gets a normal dependency with upstream CI. Cons: the owners wrote "No Rust websocket/RPC transport... No Rust btcli" (spec §3) and run the crate as a Python-wheel core; timeline is theirs; even published, the crate stays sync and `Value`-shaped, so rtao would still build its typed/async layer on top. Verdict: worth a low-cost ask (an issue proposing crates.io publication of the compute core with `host` off by default), but do not block on it.

**(c) Mirror/fork as an rtao-owned crate with a sync script.**
- Pros: full control (replace deps, make it async, publish). Cons: forking `runtime/`+`codec/`+`client.rs`+`transaction.rs` (~250 KB of source shaped by the Python seam) means owning a second SCALE engine next to subxt's `scale-value`/`scale-decode`, re-vendoring `w3f-bls` and the `tle` rev, and continuously reconciling upstream refactors that are driven by Python needs (name maps, cyscale shapes, GIL-release batching). The "sync script" would mostly produce conflicts in code rtao does not want. Verdict: do not fork wholesale.

**(d) Reimplement selected pieces against the same fixtures (recommended).**
- Use subxt (metadata-driven, async, typed codegen, v4/v5 extrinsics, subscriptions) for transport/codec/extrinsics/storage; verify rtao's output against `golden.json` (`calls[*].data_hex`, `storage_keys[*].key_hex`, `signature_payloads[*].payload_hex`, `extrinsics[*].extrinsic_hex`, `multisig[*]`) and the ledger proof vector, and add the live-chain extension table (`$META/finney.json`) to rtao's own tests.
- Port, with Apache-2.0 attribution, the small self-contained modules whose value is the format knowledge: `keyfiles/mod.rs` (NaCl via `crypto_secretbox`+`argon2` with libsodium's `argon2i13` parameters, Ansible Vault, Fernet/PBKDF2 — pure-Rust crates avoid libsodium/OpenSSL; this is the piece that most needs new cross-implementation vectors because none exist upstream), `keys/encrypted_json.rs`, `timelock/{constants,epoch_schedule,epoch_schedule_vectors}.rs` + the ~60-line tlock wrapper (keeping the same `tle` git rev + vendored `w3f-bls` until crates.io `timelock` is proven equivalent), `mlkem/mod.rs` (60 lines over `ml-kem`+`chacha20poly1305`+`twox-hash`), `pow/mod.rs` (CPU seal), `signers/{hid,ledger}.rs` (or `ledger-transport-hid`), `digest/mod.rs` (thin `merkleized-metadata` wrapper), `multisig_account_id`. Keep a `scripts/upstream-diff` that diffs exactly these upstream files at a pinned monorepo tag and fails CI when they change, so chain-side format changes are noticed.
- Keep the shape corpus out: rtao should not reproduce cyscale shapes; it only needs byte-level encode equality (goldens) and its own typed decode tests.
- Pros: 100% Rust, async, publishable, typed, no fork sp-core/C deps (only `ml-kem`, `chacha20poly1305`, `argon2`, `crypto_secretbox`, `schnorrkel`, `merkleized-metadata`, `tle`-or-`timelock`, `hidapi` optional); fixtures reused as-is. Cons: rtao owns the correctness of roughly 2-3k lines of format code (counting the upstream files' in-file tests) and must re-derive keyfile vectors (e.g. generate them once with the published `bittensor-core` wheel and commit them); timelock keeps one git dependency until the crates.io `timelock` question is settled.

## 10. Latent issues / risks noticed while reading (for whoever reuses the code)

1. `decode_extrinsic` treats any version byte without the `0x80` bit as a bare call (`codec/extrinsic.rs:335-345`); a v5 "general" transaction (declared possible by finney's `extrinsic.versions = [4, 5]`) would be mis-parsed rather than rejected.
2. `Runtime::parse` rejects V16 and relies on `Metadata_metadata_at_version(15)` (`runtime/mod.rs:193-198`, `client.rs:1238`).
3. Timelock unit tests need internet (drand) (`timelock/mod.rs:340-369`).
4. `save_password_to_environment` uses `std::env::set_var` with an acknowledged thread-safety caveat (`keyfiles/mod.rs:134-136`).
5. `query_map`/`query_batch` send every key in a single `state_queryStorageAt` (`client.rs:849-895`) — fine on localnet, unbounded on big maps.
6. `Client::sign_extrinsic` hard-codes `tip = 0` and `metadata_hash = None` (`client.rs:530-538`), so the Ledger/`CheckMetadataHash` path exists only in Python glue.
7. `set_hyperparameter`'s name→call table (`transaction.rs:670-697`) is hand-maintained and already narrower than the Python catalogue.
8. `generate_commit_v2` mixes wall-clock time, `f64` block times and a hand-ported epoch simulator that ignores `MaxEpochsPerBlock` (`timelock/mod.rs:173-184`, `epoch_schedule.rs:72-75`).
9. The `freeze_struct` hashes for `WeightsTlockPayload` differ between SDK and pallet (`705b0f6dde3ed6e` vs `b6833b5029be4127`) despite identical fields, so the macro does not actually tie the two copies together.
10. pyo3 0.23 carries two accepted RUSTSEC advisories (`cargo-audit.yml:66-67`).

## Appendix A. Byte-format quick reference (all from `$CORE/src`)

- ss58: `base58(prefix(1-2) ++ pubkey(32) ++ blake2b512("SS58PRE" ++ prefix ++ pubkey)[0..2])`; prefix ≥ 64 uses the two-byte encoding at `keys/mod.rs:62-70`.
- Keyfile NaCl: `"$NACL" ++ nonce(24) ++ xsalsa20poly1305(argon2i13(password, salt=13 71 83 df f1 5a 09 bc 9c 90 b5 51 87 39 e9 b1, SENSITIVE/SENSITIVE), json)`.
- Keyfile Fernet: Fernet token (`gAAAAA...`) with key `urlsafe_b64(pbkdf2_hmac_sha256(password, "Iguesscyborgslikemyselfhaveatendencytobeparanoidaboutourorigins", 10_000_000, 32))`.
- Keyfile JSON keys: `accountId`, `publicKey`, `secretPhrase`, `secretSeed`, `privateKey`, `ss58Address` (also `" ss58Address"`), `cryptoType` (0 = ed25519, 1 = sr25519; number or string).
- tlock: `tle::<TinyBLS381, AESGCMStreamCipherProvider>(quicknet_pk, esk, msg, Identity::new(b"", [sha256(round.to_be_bytes())]))` → `serialize_compressed`; SDK envelope `UserData { encrypted_data, reveal_round }` (SCALE); weights payload `WeightsTlockPayload { hotkey: Vec<u8>, uids: Vec<u16>, values: Vec<u16>, version_key: u64 }` (SCALE).
- Drand quicknet: genesis `1_692_803_367`, period 3 s, chain hash `52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971`; commit-v2 round = `floor((now + (first_reveal_block + 3 - current_block)*block_time - genesis)/3)`.
- Shield blob: `twox_128(pk)(16)? ++ kem_len u16 LE ++ kem_ct ++ nonce(24) ++ XChaCha20Poly1305(key = shared_secret, aad = [])`; `KDF_ID = "v1"`.
- PoW v1: `work = keccak256(sha256("subtensor-pow-register-v1" ++ netuid u16 LE ++ block_hash(32) ++ hotkey(32) ++ coldkey(32) ++ nonce u64 LE))`, valid iff `LE(work) <= U256::MAX / difficulty`; work must be ≤ 5 blocks old (`POW_MAX_WORK_AGE_BLOCKS`).
- Signature payload: `call ++ [era][nonce][tip][mode] ++ [spec_version][tx_version][genesis][era_hash][metadata_hash?]` in metadata extension order; blake2b-256 when > 256 bytes. Extrinsic v4: `compact(len) ++ 0x84 ++ MultiAddress::Id(pk) ++ MultiSignature(variant = crypto type, 64 bytes) ++ extra ++ call`.
- Multisig: `blake2_256("modlpy/utilisuba" ++ compact(n) ++ sorted_account_ids ++ threshold u16 LE)`.
- RFC-0078 `ChainInfo` for Bittensor: spec name `node-subtensor`, prefix 42, decimals 9, symbol `TAO`.
- Ledger generic app: CLA `0xF9`, path `m/44'/354'/account'/0'/index'` (20 LE bytes), sign message = `payload ++ SCALE(MetadataProof{proof, extrinsic, extra_info})` in 250-byte chunks, 65-byte `MultiSignature` reply.
