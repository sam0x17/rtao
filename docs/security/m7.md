## Finding S7-01 — low — plaintext owners can be freed without wiping

Status: source repair re-reviewed in the recorded snapshot; execution outstanding. The original vulnerable working-tree read preceded hashing, so the hashes below identify the repaired source rather than the earlier observation.

The original `seal_with_block_time_at` implementation copied the borrowed plaintext into an ordinary `Vec<u8>` before moving it into the blocking encryption closure. Successful encryption, a core error, or an abandoned blocking task therefore freed that wrapper-owned allocation without wiping it. The CLI's `Zeroizing<Vec<u8>>` protected its separate input allocation, not this copy. The original decryption closure similarly returned an ordinary plaintext `Vec<u8>` through a `JoinHandle`; when the caller's deadline or cancellation discarded that result, the wrapper had no wiping owner for it. `rtao_core::offload` is a direct `spawn_blocking(work).await`, so it adds no erasure behavior.

The prompted encryption path also called ordinary `ask_with`. That helper owned the terminal answer in a plain `String`, cloned its stripped text, and freed the original before the command guarded the returned copy. Omitting plaintext from prompt history did not wipe this earlier allocation. This was a heap-retention issue; no logging or remote-disclosure path is asserted.

The strongest defense was that a successful decryption deliberately transfers plaintext ownership to its caller, and the CLI promptly guards that result. That defense covered the returned value after a successful await, but not the extra encryption copy, discarded blocking result or original prompt buffer.

The repair now guards the copied encryption input before queuing it (`timelock.rs:417`) and returns `Zeroizing<Vec<u8>>` across the blocking decryption result boundary (`timelock.rs:517`). Ownership is transferred only after the successful await, with no further suspension before delivery. `ask_with` guards the original terminal answer (`prompt.rs:360`), while the command still guards its returned plaintext. Re-reading normal, error and cancelled-result ownership found no residual defect in these paths. This is a source conclusion, not a memory-erasure experiment.

This finding is separate from the previously tracked S02 upstream scratch limitation. It does not claim that upstream cryptography, transport/framework copies, allocator memory or OS buffers are erased.

The stale-answer candidate was checked against both protocols. Extension forwarding generates a server request ID, binds it to the browser generation, and removes pending state on cancellation/replacement. Vault removes pending state and retires an unfinished tab on timeout, cancellation or page error; the pinned page emits one answer per completed scan. A late signature for different bytes cannot pass local/client signature checks. No additional concrete stale-answer finding survived.

The PID-file candidate was checked against the lock reservation and cleanup paths. The guard does not remove a replacement token/PID blindly, and a non-daemon foreground process is not treated as a restart target. Same-user hostile process control, PID races outside the checked interval and OS/browser behavior remain outside an executed guarantee.

Authored fixtures describe cancellation, connection/request bounds, stale sessions, origin/Host rejection, file aliases/permissions, Ledger operation-lock retention, proof/digest vectors, signature verification, lazy acquisition/account mismatch, and drand deadlines/TLS/failover. Inspecting those fixtures establishes their intended assertions only. CI execution, fresh Python parity evidence, device/emulator signing, browser lifecycle and native Keychain execution are still needed. This report supplies no execution result or milestone sign-off.
