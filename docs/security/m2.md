# M2 local security review

Reviewer: an independent reviewer (not the author), who did not implement the
reviewed wallet, signer, codec or submission sources. Review date: 2026-10-14.

This is a review of the uncommitted M2 source on top of
`7efef6f68eedc7cfb85e6e9d0a5ae3da7c8d442a`. No previous milestone release tag
exists. A final milestone commit and release diff are therefore unavailable.
The findings describe the initial source snapshot and later verification.
M2-S01, M2-S03, M2-S04 and M2-S05 have committed source repairs. Current
hosted validation and dispositions are recorded in the final section; earlier
test records below describe their own snapshots. M2-S02 is **fixed** by the
combined core patch at fork revision `626f2a4f1f67ab731c1fc3884828751496bc125d`;
the [final M2-26 security pass](#final-m2-26-security-pass-2026-10-17)
confirmed and repaired four further low-severity findings. Earlier statements
that M2-S02 was open describe their own snapshots. M2-26 is complete.

The focus is PLAN M2-26: keyfile loading and the portable JSON codec, password
resolution, secret ownership and redaction, and signing. I read the complete
wallet and signer modules, their tests, both staged keyfile modules, the core
keyfile differential test, and client nonce/submission implementations twice
in order. The second pass tried to disprove each concern. Targeted checks then
followed surviving concerns into the exact locked dependency sources,
submission tests and executor. No prior execution report was consulted before
the two source passes ended. No persistent memory or repository instruction
file was consulted for the review.

## Findings

### M2-S01: malformed secret URI reaches error output

Severity: high. Resolution: fixed in
[`450c914`](https://github.com/sam0x17/rtao/commit/450c914335daa6a5da76a6c30908186e84f05e6e),
with D-036 registered. See the current hosted disposition below.

**Classification:** Verified factual or empirical problem.

**Target:** At initial review,
[signer URI construction](../../crates/rtao-signer/src/lib.rs#L236)
and [wallet URI regeneration](../../crates/rtao-wallet/src/wallet.rs#L407)
forwarded the core's error. At the locked core's
[URI derivation](https://github.com/RaoFoundation/subtensor/blob/850f2755bb05a3851f948489f0ab27b0645cebce/sdk/bittensor-core/src/keys/mod.rs#L263),
both algorithms format the dependency error with `Debug`.

**Strongest answer in the artifact:** `KeypairSigner` Debug prints only a public
account, scheme and redaction marker. Passwords and recovery inputs use secret
containers. Wrong-password diagnostics retain only the selected source.

**Ownership and perspective audit:** The caller supplies a secret URI. The
dependency parser copies that entire URI into its error; core formats that
copy into a plain diagnostic String. The SDK caller can then print or log
`SignerError` or `WalletError`, including via derived Debug.

**Precise remaining failure:** sp-core's
[InvalidCharacterInfo](https://github.com/RaoFoundation/polkadot-sdk/blob/cacb4310f20c7cac83eb3ccd8ed5a5ad4212608a/substrate/primitives/core/src/address_uri.rs#L83)
stores the original input and derives Debug. A public test mnemonic followed
by `///public-disposable-password` and a newline fails URI parsing; the exact
core formatter includes both the phrase and password for Ed25519 and Sr25519.
Secret-container redaction does not apply to the newly allocated error String.
A bounded Rust probe verified that dependency behavior without reading any
wallet or process secret. The codec's secret-seed hex error also interpolates
an offending input character, though this does not reveal an entire seed.

**Proportionate remedy:** Sanitize secret-derived errors before they leave the
signer, wallet and codec boundaries. Preserve error categories and use stable
diagnostics without input fragments. Add Display and Debug regressions for
both algorithms and wallet regeneration using only public test inputs.
Record the intentional Python diagnostic divergence as D-036.

Independent fix verification: signer and wallet URI, mnemonic, seed,
private-key and encrypted-JSON derivation failures pass through the staged
fixed-message sanitizer. It wipes the owned core diagnostic before discarding
it. The codec's malformed seed and unknown-field diagnostics also remove input
fragments. `constructor_error_chains_redact_uri_phrase_password_and_seed_sentinels`,
`regeneration_error_chains_redact_disposable_secret_input_sentinels` and
`encrypted_import_error_chains_redact_json_and_passphrase_sentinels` passed on
current Rust and Rust 1.89. The tests inspect Display, Debug and all error
sources, while valid password-URI derivation remains equal to core. The raw
signer and wallet redaction logs are not retained in the repository.
The updated Rust 1.89 pinned-core differential suite also passed four tests
with one child-only ignored entry; its parent test invokes that entry with a
disposable environment value. Its raw log is not retained in the repository.

### M2-S02: Ed25519 signing material is not wiped on final drop

Severity: medium. Resolution: **fixed** by the combined core patch pinned at
`sam0x17/subtensor` revision `626f2a4f1f67ab731c1fc3884828751496bc125d`
(see [Final M2-26 security pass](#final-m2-26-security-pass-2026-10-17)).
The analysis below describes the original locked core at v478.
Filed as [subtensor#3251](https://github.com/RaoFoundation/subtensor/issues/3251)
after duplicate searches and confirmation that current `main` still uses the
reviewed ownership model.

**Classification:** Verified factual or empirical problem.

**Target:** At initial review,
[KeypairSigner](../../crates/rtao-signer/src/lib.rs#L212) promised
upstream secret zeroization. It retains an `Arc` of the locked core's
[Keypair](https://github.com/RaoFoundation/subtensor/blob/850f2755bb05a3851f948489f0ab27b0645cebce/sdk/bittensor-core/src/keys/mod.rs#L147).

**Strongest answer in the artifact:** Retained mnemonic and seed fields use
`Zeroizing`, and clones share one owned keypair. The locked Schnorrkel
Sr25519 `SecretKey` and `Keypair` implementations wipe on drop.

**Ownership and perspective audit:** After the final signer or wallet cache
owner drops, Rust destroys and frees the core allocation. The separate
Ed25519 pair owns the signing seed, scalar and nonce prefix. Those fields are
outside the optional zeroizing mnemonic/seed containers.

**Precise remaining failure:** The locked
[sp-core Ed25519 Pair](https://github.com/RaoFoundation/polkadot-sdk/blob/cacb4310f20c7cac83eb3ccd8ed5a5ad4212608a/substrate/primitives/core/src/ed25519.rs#L55)
is `Copy`. Its Ed25519-Zebra 4.2.0 `SigningKey` derives `Copy`, `Clone` and
`Zeroize`, but has no wiping destructor. The enclosing core Keypair has no
destructor that calls its zeroization. A Rust type probe returned
`needs_drop::<ed25519::Pair>() == false` and the Sr25519 equivalent `true`.
URI-derived core keypairs retain neither optional mnemonic nor seed, leaving
no protected copy whose destructor could wipe the pair. This increases
exposure to a later memory disclosure or process dump; no remote extraction
or read of freed memory was attempted.

The downstream workspace locks Zebra 4.2.0. The corrected upstream issue also
records reproduction with the actual v478 upstream lock, Zebra 4.1.0; both
versions have the relevant fields and lack the wiping destructor. The
[corrected issue evidence](../upstream/validation/ed25519-erasure-issue.md)
distinguishes those probes. `needs_drop` establishes the destructor distinction,
not the contents of freed memory or a universal optimizer guarantee.

**Proportionate remedy:** Correct the SDK's unconditional zeroization claim
and fix ownership at the upstream core boundary. An upstream implementation
must wipe the actual Ed25519 signing object, including its expanded scalar
and prefix, on every drop. Wiping an exported seed copy is insufficient.
Keep the pinned dependency unchanged until the plan's dependency rules admit
a fix. An issue filing alone does not close this risk.

### M2-S03: codec-owned secret copies outlive zeroizing wallet buffers

Severity: medium. Resolution: fixed by the independently reviewed parser repair
in [`f16e97c`](https://github.com/sam0x17/rtao/commit/f16e97ca98d6b8790b1d0ed7cb16ed724b6777d4);
all twelve new regressions passed in the current hosted run recorded below.

**Classification:** Verified factual or empirical problem.

**Target:** The codec's [serializer](../../crates/rtao-core-ext/src/keyfile_json.rs#L199),
[JSON parser](../../crates/rtao-core-ext/src/keyfile_json.rs#L321) and
[hex seed decoding](../../crates/rtao-core-ext/src/keyfile_json.rs#L121).

**Strongest answer in the artifact:** Wallet reads, decrypted bytes and final
serialization output use `Zeroizing`. Public-field inspection separately
wipes the string values in its parsed JSON tree before drop.

**Ownership and perspective audit:** The codec allocates a new JSON tree,
hex strings, a returned private-key Vec and decoded seed Vec. These copies
are owned by the codec, independently of the wallet byte buffer and the
core's retained seed/mnemonic containers.

**Precise remaining failure:** Initial serialization inserted mnemonic and
secret hex Strings into ordinary `serde_json::Value` instances, then dropped
them without wiping. Initial decoding also dropped an ordinary Value tree
and decoded seed Vec. Wiping the input/output byte buffers could not erase those
other allocations. These codec-owned allocations now have guards. The pinned serde_json 1.0.154 Value owns plain Strings;
zeroize 1.9.1 only guarantees its explicit `Zeroize`/`Zeroizing` operations,
including their documented limits around previous reallocations. This finding
does not assume that a byte buffer's wipe can protect copies elsewhere.
The remediation's Value guard leaves dependency-owned branches:
serde_json's private scratch Vec holds decoded escaped strings without a
wiping destructor, and partially constructed trees can be dropped inside
`Value::deserialize` before it returns to the caller's guard. These behaviors are in
the exact pinned [Deserializer](https://docs.rs/serde_json/1.0.154/src/serde_json/de.rs.html#31-33)
and [string reader](https://docs.rs/serde_json/1.0.154/src/serde_json/read.rs.html#521-559).
With the workspace's `arbitrary_precision` feature, Number also owns a
private decimal String, which the completed-tree guard cannot wipe. Supported
btcli recovery fields are Strings; unsupported or unknown numeric input is
outside that guard's protection.

**Proportionate remedy:** Give codec-owned secret values and raw/hex buffers
scoped wiping ownership on success and error exits. Retain the core
differential and historical-format behavior. Check parser-error ownership
separately before claiming that every serde allocation is covered. Also wipe
the reversible encoded environment value after password resolution.

Independent fix verification: scoped guards now wipe returned JSON trees,
owned serializer values, extracted private bytes, raw/hex seed buffers and
reversible environment values. Serialization counts output first and allocates
once, retaining the existing map iteration and exact encoded bytes. The
completed-tree trailing-garbage branch is fixed by installing its guard before
calling `parser.end()`; `completed_secret_tree_guard_drops_when_trailing_validation_fails`
passed in both six-test codec unit runs. Six codec integration tests also
passed on current/MSRV, covering valid retained fields, field precedence,
scheme retry, historical raw forms and redacted secret-derived failures.
The raw logs of those runs are not retained in the repository.
Those runs predate the parser repair and do not validate it.

Follow-up source repair, 2026-10-15: the codec and wallet's public inspection now
share a private, bounded JSON projection. Unescaped strings and numeric tokens
borrow the caller's buffer. Escaped strings are validated first, then decoded
into one preallocated `Zeroizing<String>`. Object keys and values retain that
ownership through duplicate replacement, partial parses and trailing-character
errors; arrays validate and immediately drop their guarded elements. This
removes serde's private scratch, partially built Value trees and arbitrary-
precision Number allocations from these two plaintext parsing paths. The
serializer still uses its existing guarded Values and exact-size output.

An independent reviewer (not the author of the repair)
found no concrete source defect in ownership, UTF-8/surrogate handling, the
127-container depth bound, crypto defaults or public alias precedence. Twelve
new regression functions cover in-place wiping before deallocation, duplicates,
all UTF-8 prefixes of nested JSON, malformed/trailing inputs, host differentials,
public fallback and the 16 MiB boundary. No local tests or builds ran for that
repair. Its required hosted compilation and execution are now recorded in the
current disposition below.

The direct codec now caps historical raw forms as well as JSON at 16 MiB;
wallet file input already had that cap. JSON keys that serde treats as private
Number/RawValue carriers are ordinary object keys, matching Python's JSON
semantics. Neither change claims to wipe caller-owned input, opaque core
Ed25519 signing fields, third-party KDF internals or chunks freed by earlier
growth of the wallet raw-reader buffer. M2-S02 was separate and open at that
snapshot; it is now fixed by the pinned combined core patch.

### M2-S04: full deadline after broadcast loses known transaction identity

Severity: medium. Resolution: fixed in
[`450c914`](https://github.com/sam0x17/rtao/commit/450c914335daa6a5da76a6c30908186e84f05e6e)
across client and executor entry points. See the current hosted disposition below.

**Classification:** Internal inference failure.

**Target:** The complete-operation wrappers in
[submit](../../crates/rtao-client/src/submit.rs#L391),
[submit_leased](../../crates/rtao-client/src/submit.rs#L420) and
[submit_signature](../../crates/rtao-client/src/submit.rs#L812), and
[OperationLimit](../../crates/rtao-client/src/submit.rs#L1144).
The executor's enclosing
[TimeBudget](../../crates/rtao-tx/src/executor.rs#L754) initially had the same
problem: its outer timeout could cancel or discard the client's known-hash result.

**Strongest answer in the artifact:** Admission timeouts after an author
attempt become `FateUnknown { hash }`; transmitted author calls are never
replayed. Unsettled leases invalidate the nonce cache synchronously. The
executor itself does not retry an ordinary Timeout.

**Ownership and perspective audit:** The client computes the signed extrinsic
hash before broadcasting. The node can accept and execute it while the
caller waits for finality. The outer deadline wrapper can cancel that wait
and return an error after the inner future holding the hash is dropped.

**Precise remaining failure:** Before the fix, the
[acknowledged-watch deadline test](../../crates/rtao-client/tests/submission.rs#L815)
recorded one submission and required an ordinary `Client::Rpc::Timeout` with
no hash. The complete-operation wrapper also enclosed reconciliation, so
expiry of that wrapper bypassed the known-hash handling. SDK consumers could
not distinguish this from a preparation timeout or recover the identity from
the returned error. An application starting a new transfer after that error
could execute the same business action twice. No automatic client resend was
alleged. The corrected working source preserves that identity, as verified below.

**Proportionate remedy:** Track whether broadcasting has begun at the outer
submission boundary. Preserve the known hash on an unresolved postbroadcast
deadline, including every submission entry point. Keep prebroadcast timeout
behavior and lease invalidation. Reconciliation must respect the remaining
full deadline; an exhausted budget must still return the known identity.
Verify a public executor entry as well as the three client entries, because
the executor's overall timeout has the same cancellation and post-result
checks around the client operation.

Independent fix verification: all three client entries retain an attempted
hash outside the cancellable operation and map post-attempt timeouts to
`FateUnknown`, including receipt resolution and reconciliation. They clear
the nonce cache and do not begin a new history scan after the full budget
expires. The executor gives the client its remaining budget without another
outer timeout around submission; planning and unlocking retain their own
budget checks. Exact-hash, one-author-call and cache-clearing assertions pass
across typed, dynamic and tool execution, with reconciliation on and off.

The current and Rust 1.89 client suites each passed 33 tests, including
`full_ack_timeout_keeps_hash_without_starting_reconciliation_after_deadline`,
`full_timeout_during_reconciliation_keeps_hash_and_clears_all_entry_leases`,
`full_timeout_during_report_resolution_keeps_hash_without_rebroadcast` and
`expired_full_budget_before_send_stays_hash_free_for_all_submit_entries`.
Both 17-test executor suites passed
`executor_deadlines_preserve_submitted_hash_across_all_entry_points`.
The raw submission and executor logs are not retained in the repository.
Strict MSRV executor
Clippy also passed. The reviewer checked the corrected public call chains
and those actual test assertions independently.

### M2-S05: password-file reads have no size or file-type bound

Severity: low. Resolution: fixed in
[`450c914`](https://github.com/sam0x17/rtao/commit/450c914335daa6a5da76a6c30908186e84f05e6e).
See the current hosted disposition below.

**Classification:** Verified factual or empirical problem.

**Target:** At initial review,
[password-file resolution](../../crates/rtao-wallet/src/password.rs#L164)
called `std::fs::read_to_string` on the selected path. The initial file's SHA-256
was `f41fe467239c875863d2a850f3b6c48cf71fed448f9751873d4c8758415ed1d7`.

**Strongest answer in the artifact:** The path is explicitly selected by the
caller or its environment, the read runs off the async reactor, and its
successfully returned contents use `Zeroizing`. The branch preserves Python's
whole-file trim behavior. Keyfile byte reads have a separate 16 MiB cap.

**Ownership and perspective audit:** An operator chooses the password path.
A deployment configuration error, oversized file or special file affects
that process's blocking worker and memory. This is not a remote unauthenticated
attack through the wallet API.

**Precise remaining failure:** The initial reader allocated until EOF, without
the keyfile reader's cap or a regular-file check. An oversized regular file
could exhaust memory; a FIFO or device could retain a blocking read. Offloading
the operation and dropping its async waiter did not stop a running blocking
worker. Invalid UTF-8 also failed before the success-only `Zeroizing` wrapper
was installed. The corrected working source closes those paths, as verified below.

**Proportionate remedy:** Read bounded bytes into wiping ownership, reject
oversized or nonregular inputs without retaining a blocking special-file
read, then validate UTF-8 and preserve the existing whole-text trim and
precedence semantics. Add regressions for the bound and special-file refusal.

Independent fix verification: the shared `read_secret_file` helper now opens
with Unix `O_NONBLOCK`, validates the opened descriptor as regular, rejects
metadata lengths above 16 MiB, and enforces the same bound during reading.
Both password and keyfile paths use it. Bytes are guarded before UTF-8
validation. Regular symlink targets, password-source precedence and whole-text
trimming remain supported. The three regressions
`password_files_reject_oversize_nonregular_and_invalid_utf8`,
`bounded_wallet_reads_reject_large_and_nonregular_files` and
`wallet_reads_allow_regular_symlinks_and_reject_fifos_promptly` passed in both
recorded current and Rust 1.89 nine-test wallet suites. The reviewer inspected
the helper and tests independently; the raw passing test logs are not retained
in the repository.

### Reviewer method

Four independent reviewers (not the authors) each read the patched source through
one lens: Ed25519 erasure, signing compatibility, keyfile/password/redaction,
and patch provenance. Three skeptics then tried to refute each reported
finding. A finding was kept only with at least two confirmations.

### Confirmed findings and repairs

All four confirmed findings are low severity and are repaired.

1. Hard-junction derivation hashed the parent seed through an unwiped SCALE
   `using_encoded` `Vec`. It now uses a fixed `Zeroizing` preimage buffer
   with identical bytes.
2. Encrypted-JSON import kept decrypted PKCS8 secrets in plain stack arrays.
   They are now `Zeroizing`.
3. `rtao_core::keyfiles` re-exports the unrepaired upstream plaintext codec
   and environment-password functions. The module rustdoc now documents this
   and points users to `rtao_core::keyfile_json` and the `rtao_wallet`
   password sources.
4. The xtask core-patch Ed25519 source guard was a substring check with a
   tautological `needs_drop` test. It is now a `syn`-based structural guard
   over every core source file. It rejects any `ed25519::Pair` type position
   or import, requires the exact `Zeroizing<SigningKey>` owner and variant,
   requires the named regression tests and vectors, and forbids the unwiped
   `using_encoded` derivation. The fork adds the tests
   `zeroize_clears_every_signing_key_secret` and
   `hard_derivation_keeps_substrate_vectors`.

### Refuted candidates

The verifiers refuted these candidates:

- Seed copies inside inherited `sp_core` `from_string` handling.
- Unnamed move copies of `Copy` values; the existing caveat about short-lived
  values covers them.
- A missing Debug test for `GeneratedKey` and `RegenerateFrom`.
- The fuzz workspace using the unpatched core.

### Remaining limits

This pass makes no claim of erasure for allocator or OS copies, stack copies
left by moving the `Copy` `SigningKey`, short-lived values inside zebra,
blake2, schnorrkel or KDF implementations, or caller-owned inputs. No hardware
or platform execution was performed.
